# Hardware-only crypto (model "C") - ATECC608

Every private key of this firmware lives in a Microchip **ATECC608A/B/C** and **never leaves it**. There is no
software mode, no jumper, no software signing code and no software fallback: without a correctly provisioned chip the
device blinks an error code and never appears on USB.

| What | Where it lives / is computed |
|---|---|
| Attestation private key (U2F + CTAP2 batch attestation) | chip, slot `SE_ATT_SLOT` (0); generated by the chip at first boot |
| Credential private key (one per credential) | chip, one slot each (`SE_CRED_SLOT_FIRST`.. , default slots 1-7) - `GenKey` creates it inside the chip |
| Every ECDSA signature (registration, assertion, attestation, certificate) | **computed by the chip** (`Nonce` pass-through + `Sign` external, one wake session) |
| Credential id | 64 random bytes from the chip TRNG; **opaque**: it contains no key material |
| Credential table (id + relying-party hash -> slot, public key) | RP2040 flash, public data only, two sectors written alternately, CRC-protected, bound to the chip serial |
| Attestation certificate | built on the device, signed by the chip, stored in flash (public). No `mkcert.sh`, no key in the firmware image |
| Randomness | RP2040 noise + the chip's TRNG mixed through SHA-256; **the chip is mandatory** - no chip, no seed |

**ES256 (ECDSA P-256) only.** That is what the chip can do; other COSE algorithms are not offered.
**Credentials are limited by chip slots**: with the default map, 7 credentials. Registering an 8th fails
(`CTAP2_ERR_KEY_STORE_FULL` / U2F `0x6A84`) until `authenticatorReset`. Change `-DSE_CRED_SLOTS= -DSE_CRED_SLOT_FIRST=` (max 14).

## What still runs on the RP2040 (and why it is not a signing key)
* SHA-256 of public/hash inputs (rpIdHash, clientDataHash, the digest to sign).
* **Signature verification** with a public key: every signature the chip returns is verified before it is released (fault/glitch guard).
* The CTAP2 **PIN protocol** (ephemeral ECDH, AES-CBC, HMAC with the PIN token) and the PIN hash - ephemeral per-session values, not credential keys. The PIN hash is in flash.
* DER encoding of the certificate and signatures.

## Wiring (Raspberry Pi Pico)
| ATECC608 | Pico | |
|---|---|---|
| VCC / GND | 3V3 (pin 36) / GND | |
| SDA / SCL | GP4 (pin 6) / GP5 (pin 7) | 4.7 kΩ pull-ups to 3V3 recommended |

Change with `-DSE_SDA_PIN= -DSE_SCL_PIN= -DSE_I2C_ADDR=` (`0x60` default; Trust&GO parts use `0x6A`).

## Chip provisioning (one time, with Microchip's tools - NOT done by this firmware)
Lock the config zone and the data zone with this configuration for slots 0..7 (slots 8-15 are not used):

| Slot | SlotConfig / KeyConfig requirement (checked at every boot) |
|---|---|
| 0 (attestation) and 1..7 (credentials) | `KeyConfig.Private=1`, `KeyType=P256 (4)`; `SlotConfig.IsSecret=1`; `ReadKey[0]=1` (external signatures allowed); **`WriteKey[0]=1` (GenKey allowed)**; **`WriteKey[1]=0` (PrivWrite forbidden - otherwise a host could inject a key it knows)** |

Slot 0 and 1..7 must NOT be readable in clear (the firmware proves it by attempting a read and requiring status `0x0F`).
Lock config, then lock data. After the data zone is locked, `GenKey` of a private key must still be permitted for these slots
(that is what `WriteKey[0]` means; check the chip datasheet for your revision). Bit positions follow Microchip's
`calib_device.h` (`ATCA_SLOT_CONFIG_GEN_KEY_MASK` = bit 8, `PRIV_WRITE` = bit 9, `EXT_SIG` = bit 0).
Locking is irreversible: do it first on a spare chip.

## Boot, fail-closed behaviour (LED blinks N times, repeating; the device never enumerates)
| Blinks | Meaning |
|---|---|
| 1 | chip does not answer (wiring / address / power) |
| 2 | not an ATECC608 (revision byte != 0x60) |
| 3 | config or data zone not locked |
| 4 | a key slot is not configured as required, or a private slot can be read in clear |
| 5 | attestation key/identity unusable (no key, certificate mismatch, chip refused GenKey) |
| 6 | communication error / CRC / unexpected status |
| 7 | a different chip than the one this device was enrolled with (serial changed) |

First boot with a new chip: the firmware stores the chip serial in the credential table, creates the attestation key
inside the chip and the certificate. A chip swap afterwards is refused (blink 7): credentials are useless without the chip.

## Reset
`authenticatorReset` (button + within 10 s of power-up) clears the credential table **and replaces every credential key in the
chip with a fresh random key** (old private keys are destroyed, not just forgotten). The attestation key is kept. PIN is cleared.

## Upgrading from earlier versions of this firmware
A software master key left in flash at `0x72000` by an older version is **erased at first boot**. Earlier software-mode
registrations cannot be carried over - re-register. The U2F counter is kept.

## Limits - read this
* **Tested only against a behavioural model of the chip and a chip test double, never against real silicon.** The command
  layer was cross-checked against Microchip's own cryptoauthlib sources (`lib/hal`, `lib/calib`). Try a spare chip first.
* The I2C bus is not encrypted: someone probing it sees public keys, digests and signatures, never private keys.
* The chip does not rate-limit signing: someone who holds the whole board can ask it to sign for any credential id they know.
  The credential table, the PIN hash and the certificate are in flash: physical access still allows deleting or replacing them
  (not extracting private keys).
* PIN protection is as before (PIN hash in flash; retry counter in flash).
* Side-channel and fault attacks on the RP2040 or the chip were not assessed.
* Licence note: `lib/cryptoauthlib` (a git submodule kept as the reference for the command layer) is under a Microchip licence
  that restricts use to Microchip devices; this firmware's own driver (`src/se.c`) does **not** use it and the submodule is not
  linked into the build. Check the licence before redistributing a binary or the submodule together with GPL code.
